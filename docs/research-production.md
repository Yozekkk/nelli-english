# Production research: single learner progress

Checked against first-party documentation on 2026-10-01. This note describes implementation choices for this repository; it is not a report that the live database or deployment has passed verification.

Implementation update: the initial invoker RPC design exposed direct table writes to `anon`. The follow-up `restrict_progress_writes` migration revoked those grants and moved the validated writer to a non-exposed `private` schema as a `SECURITY DEFINER` function with a fixed empty `search_path`. A public invoker wrapper is the only browser RPC entry point. The live security advisor and anonymous API behavior were checked separately.

## Supabase access model

- A browser may use a Supabase **publishable** key. It identifies the application, not the learner; without Auth, every visitor with the site URL and key has the same `anon` database role. The key is intentionally public. Never put a secret or service-role key in `VITE_*`. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [Vercel TanStack Start guide](https://vercel.com/kb/guide/deploy-a-tanstack-start-app-to-vercel)
- For SQL-created `public` tables, explicitly enable RLS and grant only the needed table privileges to `anon`. Grants decide whether the role can reach an object; RLS limits rows. A single-row policy can use `USING (profile_key = 'primary')` for SELECT/UPDATE and `WITH CHECK (profile_key = 'primary')` for INSERT/UPDATE. UPDATE also needs a SELECT policy. Omit the DELETE grant and DELETE policy. Add a table `CHECK (profile_key = 'primary')` as a second safeguard. [Supabase securing the API](https://supabase.com/docs/guides/api/securing-your-api), [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)
- `SECURITY INVOKER` is the recommended default for database functions. RPC functions are executable by all roles by default, so revoke `EXECUTE` from `PUBLIC`, then grant only the required RPC signatures to `anon`. Invoker functions require the corresponding table grants and policies; therefore direct Data API writes to the allowed `primary` row remain possible. RLS cannot authenticate a learner when the user explicitly rejects Auth. A definer function needs a fixed `search_path` and particular care because it runs with creator privileges. [Supabase database functions](https://supabase.com/docs/guides/database/functions), [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)

## Atomic mutations and reset

- Make a quiz completion one database RPC so the lesson attempt and cumulative answer counter commit or roll back together. Validate lesson ID `1..20`, total questions `> 0`, and correct answers `0..total` in the database. Derive the integer score from the submitted counts. Update only that lesson: `attempts = attempts + 1`, `last_score = new_score`, `best_score = GREATEST(best_score, new_score)`, and its answer fields. Increment `learner_state.total_correct_answers` by the same `correct` value inside the function. Postgres guarantees `INSERT ... ON CONFLICT DO UPDATE` performs an atomic insert or update even with concurrent callers. [PostgreSQL INSERT reference](https://www.postgresql.org/docs/current/sql-insert.html), [Supabase RPC reference](https://supabase.com/docs/reference/javascript/rpc)
- Serialize reset and mutations by locking the one learner row first (`SELECT ... FOR UPDATE`) in every mutation RPC. Reset can `UPDATE` all lesson rows back to defaults and reset learner fields in one transaction; it need not grant DELETE. **Inference:** locking in a consistent order prevents reset from interleaving with a quiz write and leaving a partly reset state. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
- Seed with `INSERT ... ON CONFLICT DO NOTHING` for the canonical learner row. Insert the 20 initial lesson rows only when the learner row was newly inserted, in the same migration transaction; subsequent deployment must never replay a destructive seed. For the supplied evidence, cumulative correct answers start at 59 even though the six known latest attempts total 44. [PostgreSQL INSERT reference](https://www.postgresql.org/docs/current/sql-insert.html)
- A client retry after an uncertain network response can count a quiz twice unless the RPC accepts and records an idempotency key. If the implementation does not add such a key, do not automatically retry a completed attempt; refetch first. This follows from the additive `attempts` and `total_correct_answers` operations.

## Deployment and verification

- Current TanStack Start and Vercel documentation uses the Nitro Vite plugin, and Vercel detects TanStack Start when Nitro produces its Vercel output. The repository's `@lovable.dev/vite-tanstack-config` already includes Nitro and comments that its default target is Cloudflare. Do **not** add a second Nitro plugin. Check the installed Lovable config's override mechanism, generated build output, actual Vercel build, and direct nested-route refreshes; a successful local Vite build alone does not establish correct Vercel routing. [TanStack Start hosting guide](https://tanstack.com/start/latest/docs/framework/react/guide/hosting), [Vercel TanStack Start guide](https://vercel.com/kb/guide/deploy-a-tanstack-start-app-to-vercel)
- `VITE_*` values are bundled into browser JavaScript; only the project URL and publishable key belong there. Vercel environment changes need a new deployment before they affect production. [Vercel TanStack Start guide](https://vercel.com/kb/guide/deploy-a-tanstack-start-app-to-vercel)
- After migration, inspect actual schema, constraints, grants, RLS policies, seed values, and `anon` behavior. Run Supabase Security Advisor and Performance Advisor against the live project; advisor checks inspect the live schema, so findings should be reported as observed rather than assumed. [Supabase Advisors](https://supabase.com/docs/guides/observability/advisors)

The [Supabase changelog](https://supabase.com/changelog.md) was checked before this note. The recent database breaking-change entry concerns Postgres version upgrades; it does not alter the access model or SQL pattern above for these new tables.

# Research for quiz history and statistics

Checked first-party documentation on 2026-10-01. This is implementation guidance for the current repository, not a live-service verification result.

## Extend the existing progress operation

The current migrations create `public.apply_progress_operation` as a narrow `SECURITY INVOKER` API wrapper over `private.apply_progress_operation`, a `SECURITY DEFINER` function with `search_path = ''`. The private function locks the one `learner_state` row, checks the operation receipt and reset epoch, then updates the lesson and cumulative correct count. This is a suitable insertion point for a future `quiz_attempts` row.

- Add `public.quiz_attempts` with `operation_id uuid PRIMARY KEY` tied to the existing `progress_operations.operation_id`, `profile_key text CHECK (profile_key = 'primary')`, `lesson_id integer CHECK (lesson_id BETWEEN 1 AND 20)`, `correct`, `total`, `score`, and `attempted_at timestamptz DEFAULT now()`. Use the same validated `p_correct`, `p_total`, and derived `v_score` values as the lesson update. Insert the attempt **inside the `p_kind = 'quiz'` branch**, after the receipt has been inserted. A duplicate operation ID already returns before that branch. The one function call therefore updates the receipt, lesson, counter, and attempt together; an uncaught PL/pgSQL error aborts the surrounding transaction. [PostgreSQL PL/pgSQL control structures](https://www.postgresql.org/docs/current/plpgsql-control-structures.html), [PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html)
- Keep the existing learner-row `FOR UPDATE` lock and reset epoch check. They serialize concurrent progress operations; PostgreSQL documents that `SELECT FOR UPDATE` locks the selected row and that `ON CONFLICT DO UPDATE` is atomic under concurrency. The `operation_id` primary key additionally prevents duplicate attempt rows. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html)
- If reset means clearing the visible quiz history, remove attempts in the **private** reset branch in the same transaction as the existing state reset. Do not grant `DELETE` to `anon`. If retaining a past archive instead, store the epoch on each attempt and filter reads to the current epoch; otherwise old attempts would reappear after reset. This is a design inference from the current reset behavior.
- Do not backfill six fabricated `quiz_attempts` from the seed. The supplied six rows are last-known results only; `59` cumulative correct answers already includes unknown prior attempts. A chart based on this table must say that history begins with newly recorded attempts, while existing course summary continues to use `learner_state` and `lesson_progress`.

## Access and function safety

- Enable RLS on `quiz_attempts`, revoke default table grants from `PUBLIC`, `anon`, and `authenticated`, and grant only `SELECT` to `anon` with `USING (profile_key = 'primary')`. There should be no direct client INSERT/UPDATE/DELETE grant or policy. Supabase separates table grants from row policies and requires RLS on exposed `public` tables. [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase securing the API](https://supabase.com/docs/guides/api/securing-your-api)
- Modify only the **private** definer function's quiz and reset branches. Supabase warns that definer functions can bypass RLS when owned by `postgres`; it recommends keeping them outside exposed schemas, setting an empty search path, schema-qualifying referenced objects, and limiting EXECUTE privileges. The current public wrapper preserves a small, callable RPC surface; keep all new writes behind its existing input validation and fixed `primary` profile. [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase database functions](https://supabase.com/docs/guides/database/functions)
- `CREATE OR REPLACE FUNCTION` with the same signature preserves the existing function owner and privileges, so check them in the live database rather than assuming a new definition has new grants. Explicitly keep `SECURITY DEFINER SET search_path = ''` and schema-qualified relation names in the migration. [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html), [Supabase database functions](https://supabase.com/docs/guides/database/functions)
- After migration, test a first quiz, replay the same operation ID, a second distinct quiz, reset, a stale-epoch write, `anon` SELECT of history, and rejected direct `anon` INSERT/DELETE. Inspect actual grants/RLS and rerun Security Advisor; advisors inspect the live schema. [Supabase RLS testing procedure](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase Advisors](https://supabase.com/docs/guides/observability/advisors)

## Charts and deployment

- This repository declares Recharts `^2.15.4`. Recharts' own accessibility note says the chart `accessibilityLayer` default is **false in 2.x** and true only from 3.0. Set `accessibilityLayer` explicitly on any new chart in this project and provide a visible textual summary or data table for the plotted values. The Recharts layer enables keyboard and screen-reader navigation; W3C recommends a text explanation or table for chart data. [Recharts accessibility wiki](https://github.com/recharts/recharts/wiki/Recharts-and-accessibility), [W3C complex images tutorial](https://www.w3.org/WAI/tutorials/images/complex/)
- Recharts `ResponsiveContainer` measures its parent with `ResizeObserver`; give the parent a real height and room to shrink inside grid/flex layouts. Avoid assuming current Recharts 3 `responsive` examples apply unchanged to this 2.x dependency. Verify a narrow viewport in the running app. [Recharts ResponsiveContainer API](https://recharts.github.io/en-US/api/ResponsiveContainer/), [Recharts accessibility wiki](https://github.com/recharts/recharts/wiki/Recharts-and-accessibility)
- TanStack Start on Vercel uses Nitro. The repository's Lovable configuration already supplies the Nitro plugin and now selects the Vercel preset when `VERCEL` is set; verify the deployment output and direct refresh of nested routes after building, instead of adding another plugin. `VITE_*` variables are browser-visible. [TanStack hosting guide](https://tanstack.com/start/latest/docs/framework/react/guide/hosting), [Vercel TanStack Start guide](https://vercel.com/kb/guide/deploy-a-tanstack-start-app-to-vercel)
